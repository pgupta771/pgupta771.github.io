02 // MY ENGINEERING PHILOSOPHY

Why I Obsess Over Determinism & Proof

Anyone can prompt an AI to generate a basic CRUD app. What separates real systems engineering is what happens under failure: when 50 threads retry the same payment key at the same millisecond, when a worker receives kill -9 mid-stream, or when a JVM is constrained to a strict 64 MB heap.

Every system I build is backed by mathematical invariants: PostgreSQL deferred constraint triggers that reject unbalanced double-entry transfers at commit time, canonical ascending UUID lock ordering that provably eliminates deadlocks, and Testcontainers chaos suites.

Zero-Deadlock Concurrency 20,000 concurrent transfers across 100 threads with 0 deadlocks.
Constant-Memory Streaming 100,000 rows processed inside a 64 MB JVM heap (27 MB peak).

PROJECT 01 OF 05 // DISTRIBUTED FINTECH INFRASTRUCTURE

LedgerCore — Double-Entry Financial Ledger & Outbox Relay

An event-driven double-entry accounting engine in Java 21, Spring Boot 3, PostgreSQL 16, and Apache Kafka guaranteeing strict conservation of money (`SUM(entries) = 0`) under extreme concurrency.

THE PROBLEM
Concurrent payment transfers on shared hub accounts cause AB-BA deadlocks, race-condition overdrafts, duplicate charges during network retries, and lost Kafka events when dual-writing.
MY ARCHITECTURAL SOLUTION
Enforced canonical ascending UUID row locking (`SELECT ... FOR UPDATE`), a PostgreSQL `DEFERRABLE INITIALLY DEFERRED` zero-sum constraint trigger, an atomic SHA-256 `Idempotency-Key` state machine, and a `FOR UPDATE SKIP LOCKED` transactional outbox relay into a replayable CQRS Kafka projector.
